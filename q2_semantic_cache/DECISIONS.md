# Q2 semantic cache -- decision log

One entry per non-obvious choice. Format: **Decision** / Alternatives / Why / Revisit when.

---

### Partition key contents

- **Decision:** every cache operation is scoped to `(tenant, model, system_prompt_hash, params_hash, embedder.model_id)`. `CacheContext` (`types.py`) carries the first four; the embedder's `model_id` is folded in by `SemanticCache.partition_key_for` because it is a property of the cache's own configuration, not of the request. Partitions are fully independent: separate `VectorIndex`, separate LRU order, separate exact-match map, separate lock. A lookup never searches outside its own partition.
- **Alternatives:** one global index with the partition fields as post-filter metadata; a coarser key (tenant + model only, ignoring system prompt/params).
- **Why:** this is the single biggest lever on risk. Two different system prompts are two different "programs" reading the same user text -- serving one prompt's cached answer under another is not a near-miss, it's a wrong answer with a plausible-looking cause. `tenant` in the key also makes cross-tenant leakage structurally impossible rather than policy-enforced: there is no code path that can search another tenant's vectors, because there is no shared index to search. `model` matters because different models answer differently at the same prompt. `embedder.model_id` matters because vectors from different embedding models are not comparable at all (different spaces) -- mixing them wouldn't just be a wrong match, the cosine numbers would be meaningless.
- **Revisit when:** partition fan-out becomes the bottleneck (many tiny partitions, e.g. one per user rather than per tenant) -- then consider a coarser key with the finer fields as a guard/post-filter instead of a hard partition boundary, accepting a small amount of engineering risk for better hit rates.

### Similarity metric + index choice

- **Decision:** cosine similarity via plain dot product (vectors are L2-normalized by every `Embedder`), computed brute-force over a dense matrix per partition (`index.py:NumpyIndex`).
- **Alternatives:** approximate nearest neighbour (HNSW via FAISS/pgvector/Qdrant); Euclidean distance; a learned re-ranker as the primary index.
- **Why:** cosine on unit vectors is what every embedding model in scope (`HashingEmbedder`, `all-MiniLM-L6-v2`, OpenAI's embeddings) is tuned to compare well under, and a dot product on normalized vectors is trivial to explain and to test exactly. Brute-force is exact -- no recall loss to reason about -- and is fast enough at the stated scale (fine to ~100k entries *per partition*; a 100k x 384 float64 matmul is single-digit milliseconds). ANN indexes trade a small, usually-invisible amount of recall for much better scaling; that trade only matters once a partition is actually that large, and it's better decided with real traffic numbers than guessed upfront. `VectorIndex` is a `Protocol`, so swapping in an HNSW-backed implementation later is a drop-in change with no callers touched.
- **Evidence:** `tests/test_index.py` (ordering, k, removal, dimension validation).
- **Revisit when:** a partition approaches ~100k live entries, or `NumpyIndex.search`/`.remove` show up in a latency budget (`remove` is O(n); `search` is O(n·dim)).

### Threshold choice + eval evidence

- **Decision:** `tau_hit = 0.92`, `tau_verify = 0.80` as constructor defaults, selected as a candidate against a false-hit-rate target of **<= 5%** (see `eval.py`'s `FALSE_HIT_TARGET`). `eval.py` sweeps `tau_hit` from 0.70 to 0.98 in steps of 0.02 and picks the lowest tau (best recall) whose *with-guards* false-hit rate clears the target; results are frozen in `EVAL_RESULTS.md`. Because precision at that point is only 0.75, the cache itself defaults to `mode="shadow"`; `mode="serve"` is an explicit deployment decision after representative validation.
- **Alternatives:** a single "similar enough" threshold with no grey zone; picking the threshold that maximizes F1 (ignores that false hits and false misses cost very different amounts here); a fixed threshold chosen by eyeballing a few examples instead of measured evidence.
- **Why:** a false hit (serving a wrong cached answer with high confidence) is a worse failure than a false miss (paying for an extra LLM call). The evaluation is written to optimize for that asymmetry directly -- false-hit rate is the primary metric, not accuracy -- and to make the choice re-derivable from data instead of a number picked by feel.
- **Evidence (real embedder, `all-MiniLM-L6-v2`, re-run 2026-09-19; full table in `EVAL_RESULTS.md`):** with guards on, false-hit rate is 0.06 at tau 0.88-0.90 and 0.02 at 0.92, so 0.92 is the lowest threshold under the 5% target and is the default. At 0.92 precision is 0.75 and recall is 0.15 (3 of 20 paraphrases served); without guards the false-hit rate at 0.92 is 0.30, so the guards remove ~90% of false hits. Mean similarity by category shows why embeddings alone are unsafe: negation pairs score 0.966 and number-change pairs 0.896, i.e. *higher* than genuine paraphrases (0.902).
- **Known misses at the chosen point (be ready to discuss):** (1) the one remaining false hit is 'How long is a marathon in kilometers?' vs 'How long is a half marathon in kilometers?' (score 0.94): the number guard needs a digit, and 'half' is a scope modifier, not a number. At tau 0.88 two more scope-change pairs slip through (bicycle/car tire, new/refurbished laptop warranty). Scope changes with no digit, negation or capitalised entity are the guards' blind spot; the answer is the grey-zone verifier and shadow-mode audits, not more regexes. (2) the entity guard wrongly rejects 3 true paraphrases (e.g. 'Who wrote Romeo and Juliet?' vs 'Romeo and Juliet was written by whom?'; 'Earth' appears on one side only), which costs recall. I did not tune the guards against this 70-pair set because that would overfit it. (3) n=70 (20 positives, 50 negatives) means each false hit moves the rate by 2 points and recall by 5; treat the numbers as directional, and re-measure on sampled production traffic in shadow mode. (4) the eval does not model the grey-zone verifier; every paraphrase scored >= 0.80, so a good verifier over [0.80, 0.92) is the main recall lever (recall is 0.85 at tau 0.80 but false-hit rate is 0.08 there).
- **Revisit when:** `[local-embed]` (or a production embedder) is available and re-run numbers say otherwise; or false-hit audits in shadow/production mode (see "shadow-mode rollout" below) disagree with the eval set.

### Guards vs. cross-encoder everywhere

- **Decision:** four cheap, deterministic, regex-based guards (`guards.py`: numbers/dates, negation parity, capitalized-entity sets, comparison/direction words) run on every candidate that clears `tau_verify`, before any hit is served. A cross-encoder or LLM judge is *not* run on every candidate -- only on the grey zone (`tau_verify <= score < tau_hit`), via the `Verifier` interface.
- **Alternatives:** run a cross-encoder re-ranker on every top-k candidate; skip guards and rely entirely on threshold tuning; skip guards and rely entirely on the verifier.
- **Why:** the failure modes guards target (a number, a negation, a named entity, a direction word changing) are common, cheap to detect with a regex, and are exactly the differences embeddings are documented to blur. Running them on every above-`tau_verify` candidate costs microseconds. A cross-encoder on every candidate would cost a second model's worth of latency on the *entire hit path*, including the common case that's already unambiguous -- that cost belongs on the grey zone only (see next entry), not universally. Guards are not a substitute for a verifier or vice versa: guards catch categories a similarity score structurally can't distinguish (bag-of-tokens differences); a verifier/cross-encoder catches genuine ambiguity a human would also have to think about. Both run; neither is skipped because of the other.
- **Evidence:** `tests/test_guards.py` (one hard-negative test per guard: Austria/Australia, Python/Java, top-5/top-10, 2023/2024, "is X safe"/"is X not safe", buy/sell), plus `tests/test_cache.py::test_guard_rejects_hard_negative_even_above_tau_hit`, which forces a 0.97 embedding score on a number-changed pair specifically to prove the guard overrides a confident-looking score.
- **Revisit when:** the guard false-hit contribution in `EVAL_RESULTS.md`'s "with guards" column stops mattering (i.e. real embeddings already separate these categories cleanly) -- unlikely, but re-derive from data, don't assume.

### Grey-zone verifier

- **Decision:** `Verifier` is a `Protocol` (`same_intent(a, b) -> bool`). The default is `NoopVerifier`, which always returns `False` -- i.e., out of the box the grey zone behaves exactly like "below `tau_hit`": always a miss. `LLMJudgeVerifier` (real LLM/cross-encoder judge) is provided but takes its model call as an injected `judge_fn`, so constructing it requires no network and importing `verifier.py` requires no SDK.
- **Alternatives:** no grey zone at all (a single hard threshold); default to an *optimistic* verifier (serve unless proven different); always call a real judge in tests.
- **Why:** shipping `NoopVerifier` as the default means adding the grey zone can only ever make the cache *more* conservative than a bare `tau_hit` cutoff -- it introduces a new place to say no, never a new place to say yes, until someone deliberately wires in a real verifier. That is the safe direction to default in. Injecting `judge_fn` rather than constructing an LLM client inside the class keeps `semantic_cache.verifier` (and everything that imports it, including `cache.py`) importable and testable with zero network or API-key dependency, per the "tests need no network" hard rule.
- **Evidence:** `tests/test_cache.py::test_grey_zone_rejected_by_default_noop_verifier` and `::test_grey_zone_confirmed_by_permissive_verifier` (a hand-built always-agree verifier, not `LLMJudgeVerifier` -- that class is never constructed by the test suite).
- **Revisit when:** grey-zone volume is high enough that verifier latency/cost matters in aggregate -- then consider a cheaper local cross-encoder instead of an LLM judge, still behind the same `Verifier` protocol.

### What's not cacheable

- **Decision:** `policy.is_cacheable` (`policy.py`) refuses, before lookup or storage work runs: time-sensitive queries (regex for today/now/current/latest/live/breaking/"this week|month|year"), personal queries (regex for my/mine/me/myself/I and contractions), queries containing an email or a phone number, requests with `has_tools=True`, and requests with `temperature` above a configurable threshold (default 0.3).
- **Alternatives:** let the similarity threshold implicitly handle these (a "what's the current price" query would rarely match anything anyway); classify cacheability with a small model instead of regex.
- **Why:** these are refused by *kind*, not by similarity score, because a similarity match can't fix a category error: even a perfect semantic match to a cached "current price" answer is stale by definition, and a "my order status" query is inherently non-shareable across askers regardless of how it's phrased. Tool calls and high temperature are refused because the params that would make the response comparable across requests (a tool's live output, high-temperature sampling variance) aren't captured by `params_hash` alone in a way that makes two calls' outputs interchangeable. Running this check first, before any embedding or index work, also makes it the cheapest possible rejection.
- **Evidence:** `tests/test_policy.py`; `tests/test_cache.py::test_policy_runs_before_semantic_match` proves the check runs even when a near-perfect (0.99) embedding match exists.
- **Revisit when:** a tenant needs a narrower or looser policy than the global regexes give (`is_cacheable(query, ctx, ...)` already accepts `ctx` for this reason but doesn't use it yet -- see README "Known limitations").

### Single-flight model

- **Decision:** `client.py:CachedLLM` coalesces concurrent eligible identical misses (same partition, same original query) with a `threading.Lock`-guarded registry of `threading.Event`s. The first caller makes the real `llm_call`, stores the result, and wakes followers. Policy-refused requests execute independently so side effects, personal requests, and high-temperature generations are never coalesced.
- **Alternatives:** asyncio (`asyncio.Lock`/`asyncio.Future`); no single-flight (accept redundant upstream calls); a distributed lock (Redis) for multi-process deployments.
- **Why:** `llm_call` is a plain synchronous callable in the shape most LLM client SDKs already expose, and the GIL makes the registry insert/remove atomic without extra coordination -- a thread blocked on `Event.wait()` costs a stack frame, not an event-loop task. asyncio would need the same algorithm but would force every caller of `CachedLLM` onto an event loop and onto an async `llm_call`, which is a bigger API commitment than this problem asks for. In-process only: a multi-process or multi-host deployment would need a distributed lock (or just accept some duplicate upstream calls across processes, which is a much smaller problem than duplicate calls within one hot process during a traffic spike).
- **Evidence:** `tests/test_client.py::test_single_flight_deduplicates_concurrent_identical_misses` (10 concurrent identical misses -> `llm_call` invoked exactly once); `::test_upstream_exception_propagates_to_all_waiters` (a failing leader's exception reaches every waiter and never poisons the cache).
- **Revisit when:** the deployment is multi-process/multi-host and duplicate upstream calls across processes start to matter -- add a distributed lock (or accept the cost, since single-flight is an optimization, not a correctness requirement).

### Shadow-mode rollout

- **Decision:** `SemanticCache.mode` is `"serve"` or `"shadow"`, with `"shadow"` as the safe default. In `"shadow"`, `lookup()` still runs the entire decision (policy -> exact -> embed/search -> threshold -> guards -> verifier), still updates the normal metrics counters (so `hits_exact`/`hits_semantic`/`guard_rejections`/etc. reflect what *would* happen), and additionally appends a `ShadowLogEntry` to `cache.shadow_log` -- but the value returned to the caller is always `Miss(reason="shadow_mode", ...)`. `store()` is unaffected by `mode` except that cacheability policy still applies; the cache fills with eligible requests so shadow evaluation has something to match against.
- **Alternatives:** no shadow mode (go straight to serving); a separate `would_serve()` method the caller has to remember to call instead of `lookup()`; sampling (shadow only some fraction of traffic).
- **Why:** this is the rollout story the brief specifically asks for. A new deployment, a new tenant, or a newly lowered threshold is exactly the situation where you want real traffic's worth of "what would this have done" data before it can affect what any user sees. Making shadow mode a single flag on the existing `lookup()` call (rather than a second method) means the caller's code doesn't change between shadow and serve -- only the mode flag does -- which is what makes flipping it a safe, reviewable, one-line change instead of a code migration.
- **Evidence:** `tests/test_cache.py::test_shadow_mode_never_serves_but_tracks_would_be_hits`.
- **Retention:** `cache.shadow_log` is a bounded deque (1,000 observations by default, configurable). Policy-refused queries never enter it. Export eligible observations to an external audit pipeline when longer retention is required.

### Reused ideas from Q1, reimplemented (not imported)

- **Decision:** per-entry TTL with lazy expiry (checked at `_is_expired`, boundary counts as expired -- `clock() >= expires_at`) and capacity-bounded LRU eviction, per partition. The eviction structure is a plain `collections.OrderedDict` per `_Partition` (`order`, MRU moved to the end on every hit/store), not a hand-rolled doubly linked list.
- **Alternatives:** import `q1_lru_ttl` directly; hand-roll the same sentinel-headed DLL Q1 uses.
- **Why not import Q1:** `q1_lru_ttl` is owned by a different work package running in parallel (per `_SHARED.md`/the brief) and isn't a stable dependency during that work -- this folder only ever imports its own code plus `numpy`.
- **Why `OrderedDict` here instead of a hand-rolled DLL:** Q1's brief is explicit that the hand-rolled DLL is the point of that problem -- the interview conversation about it belongs to Q1's `README.md`/`DECISIONS.md`, not here. This module needs *a* working O(1)-amortized recency structure, not a second telling of the same data-structure lesson; `OrderedDict.move_to_end`/`popitem(last=False)` give O(1) amortized operations with far less code to get wrong. TTL boundary semantics (`>=` means expired) are kept identical to Q1's stated convention on purpose, so the two problems don't quietly disagree about what "expired" means.
- **Evidence:** `tests/test_cache.py::test_ttl_expiry`, `::test_ttl_none_never_expires`, `::test_capacity_eviction_evicts_lru`.
- **Revisit when:** never, unless Q1's semantics change and this should track them for consistency.

### `Hit` carries an `entry_id`

- **Decision:** `types.py`'s `Hit` has a fifth field, `entry_id: str = ""`, in addition to the four the brief specifies (`response, score, matched_query, reason`). It's given a default so `Hit(response, score, matched_query, reason)` still constructs positionally exactly as specified.
- **Why:** `feedback(entry_id, good)` and `invalidate(entry_id)` need an id to act on, and the only place that id can come from is the `Hit` that was served. Without it, a caller that wants to report "this cached answer was wrong" would have no handle to do so.

### Normalization scope: exact-match only, not semantic

- **Decision:** the exact-match and single-flight keys preserve the original text. `normalize_query` remains an identity helper for compatibility. Every textual variation goes through semantic matching and guards.
- **Why:** punctuation, case, spaces, and Unicode compatibility characters can all carry meaning: `1.5` differs from `15`, `Foo` from `foo`, and `x²` from `x2`. Lossy normalization must not bypass the safeguards used for semantic candidates.
